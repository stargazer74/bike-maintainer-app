# App v1 – Fahrzeugliste und Fahrzeug-Detail (#10) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Der Platzhalter-Startbildschirm wird zur Fahrzeugliste mit dringendstem Status; ein Tipp öffnet das Fahrzeug-Detail mit seinen Wartungsaufgaben (Status, Rest-km/Resttage, Fortschritt, fällige zuerst).

**Architecture:**
- Die Status-Logik ist eine reine Funktion in `domain`: dringendster Status, Anzahl fälliger Aufgaben, Sortierung. Den Status selbst berechnet der Server.
- `VehicleRepository` und `MaintenanceRepository` werden wie `AuthRepository` zu Interfaces mit `Api…`-Implementierung, damit ViewModels Fakes bekommen.
- Die Liste lädt Fahrzeuge und danach die Aufgaben je Fahrzeug parallel. Die API hat keinen Sammel-Endpunkt; für v1 ist das bei wenigen Fahrzeugen in Ordnung.
- Je Bildschirm gibt es ein ViewModel mit `StateFlow` (Laden / Daten / Fehler) und ein Composable mit zustandslosem `…Content` für Tests.

**Tech Stack:** wie #9: Compose + Material 3 (BOM 2026.09.00, `PullToRefreshBox`), Navigation Compose 2.10.2, lifecycle-runtime-compose 2.11.0 (`LifecycleResumeEffect`), Robolectric 4.17, navigation-testing 2.10.2. Keine neuen Abhängigkeiten.

**Spec:** `docs/specs/2026-11-06-app-v1-design.md` (Abschnitte „Fahrzeugliste“, „Fahrzeug-Detail“ ohne die Knöpfe aus #11, „Fehler im Betrieb“, „Aufbau“, „Tests“) · Ticket stargazer74/bike-maintainer-app#10 · baut auf #8 (`data.*`, `domain`) und #9 (Navigation, Theme, `ui.common`).

## Global Constraints

- **Privacy first:** keine neuen Abhängigkeiten, keine Dritt-Anfragen. Fahrzeug- und Aufgabennamen kommen nicht in Logs.
- **Texte:** nur aus `values/strings.xml` (en) und `values-de/strings.xml` (de), gleiche Schlüssel (Lint `MissingTranslation`). Zahlen werden mit Tausenderpunkt nach App-Sprache formatiert (`NumberFormat.getIntegerInstance(locale)`, also „12.345 km“ bzw. „12,345 km“). Für Tage gibt es Singular und Plural.
- **Status-Texte wie in der Web-App** (`taskStatus.*`), de / en, `%1$s` ist der formatierte Wert:
  - OVERDUE + km: „Überfällig um %1$s km“ / „Overdue by %1$s km“
  - OVERDUE + Tage: „Überfällig seit %1$s Tagen“ / „Overdue by %1$s days“; Singular „Überfällig seit %1$s Tag“ / „Overdue by %1$s day“
  - DUE_SOON + km: „Fällig in %1$s km“ / „Due in %1$s km“
  - DUE_SOON + Tage: „Fällig in %1$s Tagen“ / „Due in %1$s days“; Singular „… Tag“ / „… day“
  - OK + km, noch nie gemacht: „Erstfällig in %1$s km“ / „First due in %1$s km“; Tage: „Erstfällig in %1$s Tagen“ / „First due in %1$s days“; Singular „… Tag“ / „… day“
  - OK + km: „OK (%1$s km verbleibend)“ / „OK (%1$s km left)“; Tage: „OK (%1$s Tage verbleibend)“ / „OK (%1$s days left)“; Singular „OK (%1$s Tag verbleibend)“ / „OK (%1$s day left)“
  - OK ohne Restwert: „Fällig (noch nie durchgeführt)“ / „Due (never performed)“, wenn es noch keine Wartung gab; sonst „OK“ / „OK“.
  - DONE: „Erledigt am %1$s“ / „Done on %1$s“ (Datum mittellang nach App-Sprache), ohne Datum „Erledigt“ / „Done“.
  - Regeln: „Noch nie gemacht“ heißt `lastServiceMileage == null && lastServiceDate == null`. Bei OVERDUE wird der Betrag gezeigt (`-kmRemaining`). Singular gilt bei genau 1 Tag. `kmRemaining` hat Vorrang vor `daysRemaining`; der Server setzt höchstens einen der beiden Werte.
- **Weitere Texte (de / en):**
  - Statusnamen für Liste und Bedienungshilfen: „Überfällig“ / „Overdue“, „Bald fällig“ / „Due soon“, „OK“ / „OK“, „Erledigt“ / „Done“.
  - Liste ohne offene Aufgaben: „Alles aktuell“ / „All up to date“. Ohne aktive Aufgaben: „Keine Wartungsaufgaben“ / „No maintenance tasks“. Anzahl fälliger Aufgaben: „Fällig: %1$d“ / „Due: %1$d“.
  - Leere Liste: „Noch keine Fahrzeuge erfasst. Lege sie in der Web-App an.“ / „No vehicles recorded yet. Create them in the web app.“, Link „Web-App öffnen“ / „Open web app“.
  - Detail ohne Aufgaben: „Noch keine Wartungsaufgaben angelegt.“ / „No maintenance tasks created yet.“
  - Untertitel im Detail-Kopf: „%1$s • Baujahr %2$d“ / „%1$s • Model year %2$d“; ohne Marke/Modell „Baujahr %1$d“ / „Model year %1$d“.
  - Fehler: `AppError.Network` → „Keine Verbindung.“ / „No connection.“; `Http(status ≥ 500)` und `Http(-1)` → „Der Server antwortet nicht.“ / „The server does not respond.“; `CleartextNotAllowed` → vorhandener Text `error_cleartext_not_allowed` (#9); `NotFound` im Detail → „Das Fahrzeug wurde nicht gefunden.“ / „The vehicle was not found.“; alles andere → „Daten konnten nicht geladen werden.“ / „Data could not be loaded.“. Knopf „Erneut versuchen“ / „Try again“.
- **Sichtbare Aufgaben:** nur aktive (`active == true`). Inaktive Aufgaben zählen nicht für den Status und werden nicht angezeigt; sie verwaltet die Web-App.
- **Statusfarben** aus `LocalStatusColors` (#9): OVERDUE `overdue`, DUE_SOON `dueSoon`, OK `ok`; DONE in `onSurfaceVariant`. Status nie nur über Farbe: Es steht immer ein Text daneben, und der Statuspunkt hat eine Inhaltsbeschreibung.
- **Bedienung:** Touch-Ziele ≥ 48 dp, Karten mit `Role.Button`, Fehler über `ErrorText` (Live-Region), Laden über `LoadingIndicator` (`ui.common.Feedback`).
- **Gates:** Kover ≥ 90 % auf `data`/`domain` bleibt grün; Lint `warningsAsErrors`.
- **Commits:** Trailer `Co-Authored-By: opencode <noreply@opencode.ai>`, Ticket `(#10)`, Branch `feature/vehicles`.

## Review Focus

1. **Server antwortet bei einem Fahrzeug mit Fehler, bei den anderen nicht:** Die Liste zeigt dann keinen halben Stand, sondern den Fehler mit „Erneut versuchen“ (sonst hätte ein Fahrzeug fälschlich „Alles aktuell“). Test: `summariesFailWhenOneTaskListFails` (Task 1).
2. **Nach unten ziehen ohne Netz, während schon Daten da sind:** Die Daten bleiben sichtbar, der Fehler erscheint darüber. Ein fehlgeschlagenes Neuladen darf die Liste nicht leeren. Test: `refreshFailureKeepsData` (Task 2).
3. **Zurück aus dem Detail oder Rückkehr aus dem Hintergrund:** Die Liste lädt still neu, damit Änderungen aus der Web-App bzw. ab #11 sichtbar werden, ohne Ladekreisel über bestehenden Daten. Test: `silentReloadDoesNotShowSpinner` (Task 2).
4. **Sitzung läuft im Detail ab:** Die Umleitung zur Anmeldung muss auch von `VehicleRoute` aus greifen, sonst bleibt man auf einem Fehlerbildschirm hängen. Test: `loginRequiredOnVehicleDetailRedirects` (Task 4).
5. **Fahrzeug in der Web-App gelöscht, während das Detail offen ist:** 404 → „Das Fahrzeug wurde nicht gefunden.“ mit Zurück statt „Erneut versuchen“. Test: `deletedVehicleShowsNotFound` (Task 3).
